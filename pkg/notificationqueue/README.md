# Durable notification delivery

Scope: this queue serves the plaintext (non-vault) listener path only. Secure vault mode never wires it (see below). In the shipped binary APNs can be enabled only in secure vault mode (`apnsRuntimeConfigurationValid` in `cmd/server/main.go`), so on the plaintext path the queue carries FCM and HTTP deliveries; the APNs-specific parts below (plaintext token invalidation, stable apns-id, `notification_id` in the APNs payload) are reachable only if a future build allows plaintext APNs, and are covered by tests.

The server's V3 and V4 listeners first filter for this application's subscribed topics, then persist each relevant received encrypted envelope in PostgreSQL (schema `notification_queue`) before admitting it to a worker. A unique listener/message key deduplicates stream replays; the V4 key binds the originator node and sequence to a digest of the envelope bytes, so a reused originator sequence with new content is new work rather than a silent duplicate. Admission pauses on database failure or capacity exhaustion. The durable queue caps pending work at 100,000 envelopes and 512 MiB of encrypted bytes, with a 2 MiB limit per frame. It does not accumulate all traffic on unrelated network topics. Workers use expiring leases; restart recovers admitted work. Before a provider call, the worker persists the complete initial eligible-recipient set (eligibility is the same push policy the dispatcher enforces). Retries intersect that set with current subscriptions and active installations, and the first attempt's snapshot stays authoritative even if the current set later grows. Newly subscribed devices do not receive an old envelope merely because another device required retry.

Per-device receipts retain accepted and permanently rejected outcomes. Provider calls have a 15-second deadline, recipient leases last 30 seconds, envelope leases last 90 seconds with a heartbeat, and one processing attempt is bounded at five minutes. All completion writes require the captured lease generation. A receipt write is not cancelled by listener shutdown, so an acceptance that lands while the process stops is still recorded. Attempts are bounded at 12 with exponential delays capped at one hour, and pending envelopes expire after 24 hours. Terminal work immediately discards encrypted payload bytes; metadata deduplication lasts seven days. Admission, maintenance, and each worker have independent readiness state: successful idle claims cannot mask a failed admission or another worker. Failures require operational monitoring. Structured health logs distinguish envelope processing completion from recipient provider acceptance and rejection; a completed envelope does not mean every recipient received a push.

Recipient outcomes use fixed failure classes. Retried (pending): `provider_transient` (network, throttling, 5xx, and provider credential failures such as APNs 403 or FCM THIRD_PARTY_AUTH_ERROR) and `token_cleanup`. Terminal: `provider_permanent` (a provider rejection that will fail identically for this message, for example APNs 4xx other than 403 and 429, which includes BadDeviceToken, DeviceTokenNotForTopic and BadTopic, and FCM UNREGISTERED, INVALID_ARGUMENT and SENDER_ID_MISMATCH), `no_provider` (no configured provider handles the installation's mechanism) and `suppressed` (no longer eligible under push policy). A plaintext listener refuses to start with no provider at all. An envelope whose initial eligible recipients exceed 10,000 is dead with `recipient_limit`. A processing panic records the envelope dead with `processing_panic` before the listener fails closed, so a restart cannot reclaim the same poison frame.

An APNs acknowledgment means provider acceptance, not device receipt or an opened notification. A transport timeout or a crash after provider acceptance can leave an uncertain outcome. Retrying may produce another push: a stable APNs request UUID and `notification_id` payload help consumers deduplicate, but they do not promise exactly-once delivery. Client deduplication and controlled device/provider traces remain acceptance prerequisites.

APNs invalid-token cleanup keeps the installation and subscriptions intact. Only a 410 Unregistered or ExpiredToken response with Apple's invalidation timestamp retires a token, and it retires only the captured token registration version. A 410 lacking that timestamp does not retire a token. BadDeviceToken never retires a token: Apple also returns it for a sandbox/production environment mismatch (for example a TestFlight production token sent through a development-mode server), so it rejects that push and keeps the registration. The same classification governs the secure reliable APNs worker, which therefore no longer converts BadDeviceToken or DeviceTokenNotForTopic into a route erasure. Renewal increments an independent registration version even if timestamps coincide. An invalid latest token stays as a tombstone so older registrations cannot become an accidental fallback. Explicit registration can reactivate it.

The all-envelopes streams currently have no reconnect cursor. This queue protects frames already received and durably admitted; it cannot recover frames missed while disconnected or between network receipt and persistence. A separately validated XMTP history/catch-up strategy is required before claiming lossless network ingestion. Admission does one subscription lookup per relevant frame on the receive goroutine, so a slow database slows consumption, and the server may then reset the stream. A frame above the 2 MiB admission limit is never delivered: the queue records only its listener and message key as dead work with failure class `oversized` (so queue health reports it and a replay stays deduplicated), and the listener skips it and keeps consuming. One oversized frame cannot stop the listener or the durable workers.

Secure vault mode never wires this queue or the plaintext token invalidator. The vault keeps routing state in `hytch_push_vault` as keyed lookups and encrypted topics and persists per-recipient APNs delivery in its own encrypted job store; persisting raw network envelopes for subscribed topics here would reveal which topics have subscribers, and the restricted runtime role is never granted these tables. The legacy routing retirement does not drop the `notification_queue` schema; it stays empty in a database that never ran a plaintext listener.

Rollback: migrations are monotonic for running images. Once a database is at 00015, an older image cannot start against it (secure mode requires the exact embedded schema version; plaintext mode fails because golang-migrate has no file for version 15). Roll forward with a fixed image. A down-migration of 00015 drops the queue and any admitted work, so run it only deliberately, with no pending work, before starting an older image, and never on a live secure bridge database. This service's actual Hytch routing and enabled provider configuration must be established independently before activation. Local synthetic tests do not authorize deployment, provider credentials, activation, or real device notification sends.
