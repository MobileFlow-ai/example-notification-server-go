# Durable notification delivery

The server's V3 and V4 listeners first filter for this application's subscribed topics, then persist each relevant received encrypted envelope in PostgreSQL before admitting it to a worker. A unique listener/message key deduplicates stream replays. Admission pauses on database failure or capacity exhaustion. The durable queue caps pending work at 100,000 envelopes and 512 MiB of encrypted bytes, with a 2 MiB limit per frame. It does not accumulate all traffic on unrelated network topics. Workers use expiring leases; restart recovers admitted work. Before a provider call, the worker persists the complete initial eligible-recipient set. Retries intersect that set with current subscriptions and active installations. Newly subscribed devices do not receive an old envelope merely because another device required retry.

Per-device receipts retain accepted and permanently rejected outcomes. Transient failures and provider credential/configuration failures remain pending within the bounded retry window. Provider calls have a 15-second deadline, recipient leases last 30 seconds, and envelope leases last 90 seconds with a heartbeat. All completion writes require the captured lease generation. Attempts are bounded at 12 with exponential delays capped at one hour, and pending envelopes expire after 24 hours. Terminal work immediately discards encrypted payload bytes; metadata deduplication lasts seven days. Admission, maintenance, and each worker have independent readiness state: successful idle claims cannot mask a failed admission or another worker. Failures require operational monitoring. Structured health logs distinguish envelope processing completion from recipient provider acceptance and rejection; a completed envelope does not mean every recipient received a push.

An APNs acknowledgment means provider acceptance, not device receipt or an opened notification. A transport timeout or a crash after provider acceptance can leave an uncertain outcome. Retrying may produce another push: a stable APNs request UUID and `notification_id` payload help consumers deduplicate, but they do not promise exactly-once delivery. Client deduplication and controlled device/provider traces remain acceptance prerequisites.

APNs invalid-token cleanup keeps the installation and subscriptions intact. Only a 410 Unregistered or ExpiredToken response with Apple's invalidation timestamp retires a token, and it retires only the captured token registration version. A 410 lacking that timestamp does not retire a token. BadDeviceToken never retires a token: Apple also returns it for a sandbox/production environment mismatch (for example a TestFlight production token sent through a development-mode server), so it rejects that push and keeps the registration. Renewal increments an independent registration version even if timestamps coincide. An invalid latest token stays as a tombstone so older registrations cannot become an accidental fallback. Explicit registration can reactivate it.

The all-envelopes streams currently have no reconnect cursor. This queue protects frames already received and durably admitted; it cannot recover frames missed while disconnected or between network receipt and persistence. A separately validated XMTP history/catch-up strategy is required before claiming lossless network ingestion. A frame above the 2 MiB admission limit is never delivered: the queue records only its listener and message key as dead work with failure class `oversized` (so queue health reports it and a replay stays deduplicated), and the listener skips it and keeps consuming. One oversized frame cannot stop the listener or the durable workers.

Recipient outcomes use fixed failure classes: `provider_transient` and `token_cleanup` stay pending and retry; `provider_permanent` (a provider rejection that will fail identically, including APNs BadDeviceToken and DeviceTokenNotForTopic and FCM UNREGISTERED), `no_provider` (no configured provider for the mechanism) and `suppressed` (no longer eligible under push policy) are terminal. An envelope whose eligible recipients exceed 10,000 is dead with `recipient_limit`; a processing panic records the envelope dead with `processing_panic` before the listener fails closed, so a restart cannot reclaim the same poison frame.

Secure vault mode never wires this queue. The vault keeps routing state in `hytch_push_vault` as keyed lookups and encrypted topics and persists per-recipient APNs delivery in its own encrypted job store; persisting raw network envelopes for subscribed topics in these public tables would reveal which topics have subscribers, and the restricted runtime role is never granted them.

Do not roll back the database migration while admitted delivery work exists: dropping the queue destroys that work. Use app-only rollback and preserve the additive schema, with an explicit forward repair and replay procedure. This service's actual Hytch routing and enabled provider configuration must be established independently before activation. Local synthetic tests do not authorize deployment, provider credentials, activation, or real device notification sends.
